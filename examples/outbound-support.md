# 出海客服：多语言工单分流

> 中文创始人做出海产品时，把多语言工单先分流、再出回复草稿，人只审高风险与不确定项。

- **适合**：一人公司刚开始有英文/多语言咨询，还请不起专职客服
- **验证日期**：2026-10-18（**待真机验证**；本文为脱敏虚构配方草稿，产品名与样例均为假）
- **验证级别**：待验证
- **成本量级**：低

## 场景

工单语言混杂（英文为主，偶有西语/日语等），一个人既要判断优先级又要写得体回复，容易漏单或过度承诺。配方把流程拆成：脱敏导入 → 语言/类型分流 → 草稿 → 人工闸门。bot **不直接发信**；发出去的每一封都由人点确认。

## 输入

- 过去 N 小时的工单导出（邮件 / 表单 / 帮助台），**先脱敏**：去掉真实邮箱、订单号、地址、可识别姓名
- 产品事实卡：`{{产品名}}`、已上线功能列表、已知限制、退款/SLA 政策摘要（只写对外可公开的条款要点）
- 支持的回复语言：`{{默认回复语言}}`（如 English）；可选 `{{可翻译语言列表}}`
- 升级规则：涉及付款争议、安全、法律、媒体 → 一律 `[需人工]`，不生成可发送草稿

## 步骤

1. **导入脱敏**：将工单粘贴或写入 `inbox/tickets-{{日期}}.md`；真实联系方式留在帮助台，不进 bot 上下文
2. **分流**：bot 输出表格——语言、类型（bug / 需求 / 咨询 / 投诉 / 其他）、优先级（高/中/低）、是否可自动草稿
3. **草稿**：仅对「咨询 / 低优先级需求说明」写回复草稿；语气克制，不承诺未上线功能与具体上线时间
4. **翻译（可选）**：若用户非英文，先英文草稿 → 再译成目标语言；关键条款以英文事实卡为准
5. **人工闸门**：人在帮助台核对收件人与原文后，复制草稿发送或手改；高优先级与 `[需人工]` 条目当天必须人看
6. **回写**：反复改过的句子沉淀进事实卡或 prompt，减少下次幻觉

## Prompt

分流 + 草稿（可拆成两个 bot，此处合并示例）：

```text
你是 {{产品名}} 的出海客服助理（只写草稿，不发送）。
输入是已脱敏的工单列表。请输出：

1) 分流表（Markdown）：
| ID | 语言 | 类型(bug/需求/咨询/投诉/其他) | 优先级(高/中/低) | 可草稿?(是/否) | 理由 |

2) 对「可草稿=是」的每条，写回复草稿：
- 默认语言：{{默认回复语言}}
- 语气：友好、简洁、不卖弄
- 只陈述事实卡内已有信息；不确定写 [需人工]
- 禁止：承诺上线时间、编造功能、提及内部路径、索要密码/验证码、写入真实邮箱或订单号

3) 「需人工」清单：付款/退款争议、安全、法律、媒体、情绪激烈、事实卡未覆盖的问题。

事实卡：
{{产品事实卡}}

工单：
{{脱敏工单正文}}
```

人工闸门检查清单（给人看）：

```text
[ ] 收件人与工单原文来自帮助台，不是 bot 上下文里的地址
[ ] 草稿未承诺未上线功能或具体日期
[ ] 无 key / 内部路径 / 其他用户信息泄露
[ ] 高优先级与投诉类已由人处理或明确延期
```

## 产出

虚构示例（AcmeTools 为假名）：

```text
# out/support-2026-10-18.md
| ID | 语言 | 类型 | 优先级 | 可草稿? | 理由 |
| T1 | en | 咨询 | 低 | 是 | 问批量导出是否支持 CSV |
| T2 | en | 投诉 | 高 | 否 | 涉及付款，需人工 |
| T3 | es | 咨询 | 中 | 是 | 问时区显示，可译 |

草稿 T1（English）：
Thanks for reaching out. AcmeTools currently exports CSV from the Orders view
as described in our docs. If you need another format, tell us which one—
we track requests but can't commit to a date. [需人工: 是否附文档链接]

需人工：T2 付款争议 → 帮助台原单处理
```

## 坑

- **未脱敏就喂模型**：真实邮箱、订单号、姓名会进上下文甚至日志；导入前先替换为 `{{用户称呼}}` / `{{工单ID}}`
- **bot 直接发信**：最危险；连接器即便能发，也要人工闸门，本配方默认「只出草稿」
- **过度承诺**：模型爱写 “we'll fix this next week”；prompt 禁止具体日期，政策外请求一律 `[需人工]`
- **多语言事实不一致**：先定英文事实卡，再翻译；不要让模型用目标语言「自由发挥」政策
- **和一人三岗客服岗重复**：本配方专注出海多语言分流与闸门；更粗的三角色日闭环见 `one-person-three-roles.md`
- **工单 ID 混乱**：分流表 ID 与帮助台编号不一致时，人会对错单；约定 ID 前缀或只使用帮助台编号的哈希占位

---

提交前自查：无 key / token / cookie，无营收数字，无内部路径，无可识别个人信息。
